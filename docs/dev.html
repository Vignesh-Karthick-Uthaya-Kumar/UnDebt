UnDebt — Proposed dev technical design

Branch: dev · Proposed implementation, not production until merged to main. Code is authoritative; this document records current behavior and release gaps.

For technical architects, designers, and developers. The production design describes unchanged platform, schema, and current calculation baseline.

1. Solution and architecture

Extend loan setup and projection from one recurring payment to a sequence of dated payment/rate windows. Preserve Expo/React Native, Supabase Auth/Postgres, the accounts table, ownership/RLS, and current summary/chart contracts. The proposal does not add a migration: schedules are encoded in existing payments and interest_rates JSONB arrays.

2. UI behavior

  • General loan forms support one or more repayment windows with amount, payment type, frequency, start/end, and optional rate override. Eligible types can add/remove schedules.
  • Interest-only periods are separate dated ranges. Credit cards expose Min balance/Full payment and an optional 0% period, with normal-rate windows around it.
  • Buy Now Pay Later defaults to fortnightly and offers weekly/fortnightly/monthly/quarterly choices.
  • Compact mode uses a vertical scrollable sidebar. Existing screens, periods, charts, account CRUD, offsets, Save/Spend, and auth remain the product contract.

3. Data structures and persisted schema

LoanScheduleDraft is transient form state, not a table. It groups interest-only/free flags and dates, credit-card payment type, and RepaymentScheduleDraft[]. Each repayment has a transient UI ID, amount text, payment type, frequency, ISO start/end, same-rate flag, and optional rate override.

interface RepaymentScheduleDraft {
  id: string; amount: string;
  type: 'Principal and Interest' | 'Interest Only' | 'Min balance' | 'Full payment';
  frequency: string; startDate: string; endDate: string;
  sameInterestRate: boolean; interestRate: string;
}

interface LoanScheduleDraft {
  interestOnlyPeriodEnabled: boolean;
  interestOnlyStartDate: string; interestOnlyEndDate: string;
  interestFreePeriodEnabled: boolean;
  interestFreeStartDate: string; interestFreeEndDate: string;
  creditCardPaymentType: 'Min balance' | 'Full payment';
  repayments: RepaymentScheduleDraft[];
}

Example persisted schedule

{
  "payments": [{
    "type": "Principal and Interest", "periodKind": "repayment",
    "amount": 850, "frequency": "Monthly",
    "startDate": "2027-01-15", "endDate": "2056-12-15",
    "sameInterestRate": false, "interestRate": 6.1
  }],
  "interest_rates": [{
    "rate": 6.1, "date": "2027-01-15",
    "endDate": "2056-12-15", "periodKind": "repayment"
  }]
}

Interest-only entries are stored in payments. Credit-card interest-free windows are interest_rates with rate: 0 and periodKind: "interest-free"; normal rate is stored for pre/post windows. Draft IDs are not persisted keys. Existing activity entries remain in payments. Relational schema, RLS, indexes, triggers, and setup SQL are unchanged; see production DB setup.

4. Validation and date semantics

  1. Validate ISO loan start; require maturity except for CreditCard; reject end before start.
  2. Require at least one repayment; positive amount for non-card, frequency for all, and finite non-negative custom rate.
  3. Validate interest-only/free dates, schedule start/end order, loan-term bounds, and pairwise non-overlap across all periods.
  4. For dated loans require continuous repayment/interest-period coverage from max(startDate, today) through maturity.

Date utilities parse UTC calendar days, reject impossible dates, add days, and clamp month additions. A repayment’s first due date is one full frequency interval after its start date, then advances from each prior due date. Confirm this convention with product/lender requirements; month-end clamping can drift.

5. Calculation behavior and assumptions

The local simulator adds monthly interest boundaries and splits intervals at the next generated payment event. Rate segments are duration-weighted inside a month:

periodRate = Σ (annualRateSegment / 100 / 12)
                 × (segmentDuration / monthDuration)
interest = max(0, balance - offsetBalance) × periodRate
            + proratedChargeInterest

Interest is added before scheduled payment. Additional part-payments are applied after scheduled events, only in the offset-enabled/actual simulation. Projection remains capped at 30 years and existing annual chart samples remain.

Payment typeCurrent simulator behaviorImportant limitation
Full paymentPays simulated balance at each generated due dateSimplified cycle semantics
Interest Only, no amountPays accrued interest since last payment, capped by balanceAccrual/payment timing requires validation
Interest Only, amount presentPays configured amountCan differ from actual interest accrued
Principal and InterestPays configured amountNo amortization payment solver
Min balanceUses configured amount or zeroNo minimum-payment formula

Monthly repayment summary annualizes configured amounts by frequency and divides by 12; it does not prorate for active schedule windows. Existing balance, cash interest, offset allocation, Save/Spend formulas, account defaults, and 30-year horizon are described in production calculations.

5.2 Dev loan event formulas and order

Each loan starts with the balance supplied at projection start. The next interval boundary is the earliest of one calendar month, next schedule payment due date, or maturity/horizon. A schedule's first due date is one full frequency after its own start date; later dates advance from the prior due date. Monthly interest boundaries do not imply monthly payment cadence.

periodRate = Σ [(annualRate_i / 100 / 12)
                × overlapDuration_i / (nextMonthlyBoundary − cursor)]
baseInterest = max(0, simulatedBalance − offsetAtNext) × periodRate
chargeInterest = Σ [charge × periodRate × (next − chargeDate) / (next − cursor)]
interest = baseInterest + chargeInterest
  1. Sample offset at the interval end and accrue base interest for the full interval.
  2. Add dated credit-card/BNPL Bill Payment and Expense charges and prorated charge interest.
  3. At a scheduled due date, pay the lesser of balance and: whole balance for Full payment; accrued interest for amount-less Interest Only; configured amount otherwise (Min balance included). The optional interest-only-period form itself serializes an amount-less Interest Only entry, parsed as a payment schedule—not only as a rate/term flag.
  4. In actual/offset-enabled simulation only, apply linked Part Payment occurrences after the scheduled payment. Events earlier in the interval still reduce the loan only at interval end.
  5. Record balance and cumulative metrics; values at or below $0.005 become zero.

Latest rate start date not after the segment is used. A stored rate end date is not enforced; with a rate array but no started entry, selected rate is zero; without a rate array, first account rate is the fallback. The charge-interest calculation applies the interval's blended rate, rather than recalculating the exact rate segments after each charge.

5.3 Loan inputs are not amortization formulas

Input/typeCurrent simulator behavior and gap
Principal and InterestUses the amount entered literally; no principal/rate/term solver.
Interest Only, blank amountPays accumulated simulated interest at generated due events, not a lender's daily-calculated due.
Interest Only, amount suppliedPays that entered amount even if above or below accrued interest.
Min balanceUses configured amount or zero; no minimum percentage/floor/statement-balance rule. Card form has no amount field; default card schedule is blank, so default Min balance pays zero.
Full paymentPays the entire simulated balance at each event; no statement cycle, grace period, fees, or payment waterfall.
BNPL$100 fortnightly is a static form preset, not balance/term-derived; default rate is 0% from static inputs. Fees are not inferred.

The introductory interest-only entry uses the first repayment's frequency; it generates its first due date one full frequency after the period start and repeats through the configured end date. The exact intended lender timing for its first/last due events is not separately specified.

5.4 Dev-specific calculation omissions

  1. Payment summary annualizes every schedule regardless of active date range or type; extra-payment run-rate is not truncated at payoff.
  2. Monthly recurrence generation advances from the prior date (Jan 30 → Feb 28 → Mar 31), while activity counting anchors to original date (Jan 30 → Feb 28 → Mar 30).
  3. Schedule validator checks date coverage/non-overlap, but the calculator still ignores rate-window end dates; define boundaries and golden tests for promo periods, charges, same-day events, and month ends.
  4. Interest is monthly simple prorating, not APR-to-APY conversion, daily accrual, contractual day count, or daily compounding. Offset is sampled at interval end and applied for the whole interval.
  5. Shared production issues remain: balance baseline ambiguity, unspent transfers in Spend, Save end-cash wiring, first-rate display, differing projection/FY cutoffs, and inconsistent negative-balance handling. See full shared audit.

6. Database and data interactions

Account inserts/updates still write fields on public.accounts; schedule edits replace recognized prior schedule entries while retaining non-schedule activities. Interest-only windows and repayment records go in payments; repayment overrides and card promo periods go in interest_rates. RLS remains the row ownership boundary.

The array is read-modify-write JSONB, not a normalized schedule table. Concurrent edits can overwrite data; the DB cannot enforce schedule shape. Legacy object/array parsing and startDate/date aliases are accepted; malformed JSON may be treated as missing and fall back to default rates.

There is no dev-only SQL. Use the production setup reference for local Supabase commands, core DDL, CRUD query equivalents, and schema/RLS/trigger inspection. Current app configuration points to one hosted project; do not exercise dev changes against production user data—create a separate staging project/config first.

7. Gaps and production gates

  1. Blocker: Min balance has no formula; when no amount is configured the current simulated payment is zero. Implement a specified rule or explicitly exclude it before merge.
  2. Define principal-and-interest payment calculation, full-payment timing, lender day-count/compounding, rate change behavior, card statements/minimums, BNPL fees, and first due date.
  3. Rate entries store endDate, but current rate selection uses latest start date and does not itself enforce the end. Define gaps/overlaps and validate continuous rates.
  4. Add tests for legacy JSON, invalid/leap/month-end dates, schedule overlap/coverage, payment order, rate boundaries, and expected balances/interest.
  5. Verify create/edit/restore/replacement and preservation of non-schedule activity, promotional end dates, empty optional values, errors, accessibility, and compact sidebar widths.
  6. Run authenticated/anonymous RLS scenarios and review existing overlapping policies/triggers. Add CI app build/typecheck and financial tests; Pages CI is not a product build.
  7. Create a distinct staging Supabase project/configuration before shared testing; the client currently has no dev/prod project selection.

Acceptance: product signs off payment semantics; regression cases pass; legacy rows still load/edit; JSON activities are preserved; visual/accessibility review passes; production docs are updated to match exact merged behavior.

8. Dev → main release and documentation lifecycle

  1. dev is proposed/integration; main is production. Update dev MD and HTML with each material app change; the workflow enforces both.
  2. Validate via cd expoapp && npx tsc --noEmit, focused tests, app/web checks, and authenticated RLS-backed create/edit/delete scenarios.
  3. Open reviewed dev → main PR; update production MD and HTML to the exact release. The workflow enforces both on app-code PRs.
  4. Merge after review and accepted release gates. Merge updates production code and docs together; it does not deploy app binaries or apply database migrations.
  5. Static Pages site is published from branch dev, path /docs, at UnDebt design docs. The Actions workflow also validates documentation and publishes on dev pushes. Application and DB releases remain separate.
