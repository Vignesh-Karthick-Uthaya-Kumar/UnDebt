UnDebt — Proposed design

Status: Proposed changes on dev, including current in-progress worktree changes. Not production until merged to main. Keep this page and dev.md aligned with material code changes or requested refreshes.

Solution and architecture

Extend loan setup/projection to support dated repayment stages rather than one recurring payment per loan. Keep the Expo/React Native client, Supabase Auth/Postgres backend, account-row ownership, and current database table. Persist schedules in existing payments and interest_rates JSONB; no database migration is proposed. A pure TypeScript loanSchedules module handles draft creation, date helpers, and validation.

  1. The account modal initializes a schedule draft and restores staged entries when editing.
  2. Users define repayment windows (dates, amount, frequency, payment type, optional rate override), interest-only windows, and credit-card interest-free windows/minimum-or-full payment. BNPL has restricted frequency options.
  3. Client validation checks dates, amounts/frequencies, overlap, term bounds, and active-term coverage. Save serializes repayment and rate windows into account JSONB through existing Supabase writes.
  4. The projection engine processes multiple dated events, accrues interest at monthly boundaries, applies due payments, and preserves existing metrics/chart series. Compact navigation changes to a vertical scrolling sidebar.

Data structures and persisted schema

LoanScheduleDraft groups interest-only/free flags and dates, credit-card payment type, and RepaymentScheduleDraft[]. A draft entry contains transient UI ID, amount text, payment type, frequency, start/end dates, same-rate flag, and optional override. IDs in drafts are not database keys. The account JSONB remains source of truth.

payments[] = {
  type: "Principal and Interest" | "Interest Only" | "Min balance" | "Full payment",
  periodKind?: "interest-only" | "repayment",
  amount?: number, frequency: string, startDate: "YYYY-MM-DD", endDate?: string | null,
  sameInterestRate?: boolean, interestRate?: number
}
interest_rates[] = { rate: number, date: "YYYY-MM-DD", endDate?: string | null, periodKind?: string }

Interest-free periods are stored as dated zero-rate windows. Existing income, transfers, part-payments, bills, and expenses remain in payments; no new table is added.

UI and calculation rules

  • Loan forms expose payment type, frequency, dates, and multiple staged schedules. Add/remove controls vary by account type, and validation errors block save.
  • The simulator reads multiple schedule entries. Dated rates apply to their simulated period; otherwise the account rate default applies. It calculates interest on balance net of eligible offset, applies repayment events at generated schedule dates, pays accrued interest for amount-less interest-only entries, pays the remaining balance for full-payment entries, and uses configured amounts for other entries.
  • Monthly repayment summary totals annualized configured amounts across schedules. Existing balance, offset, financial-year, Save/Spend, and chart behavior remains intended.
  • Date helpers use UTC ISO calendar dates and clamp month additions. Validation requires non-overlap and repayment/interest coverage through maturity when an end date exists.

Gaps before production

  1. Add tests for validation, legacy JSON, event generation, leap/month-end dates, payment ordering, rate boundaries, and projected balances/interest. No runner or financial regression suite is present now.
  2. Confirm first-payment timing, day-count/interest accrual, intra-period rate changes, minimum-payment rules, statement dates, and BNPL fee/interest behavior with product requirements. Estimates are not lender-grade.
  3. JSONB does not enforce schedule structure; concurrent edits can overwrite arrays. Define handling for malformed legacy entries and duplicate/overlapping ranges.
  4. Verify restored legacy schedules, schedule replacement/removal, empty end dates, DST/date boundaries, narrow layouts, accessibility, and save/error flows.
  5. Recheck RLS with authenticated and anonymous test users; review deployed overlapping policies/triggers. A future normalized schema requires reviewed migration and backfill.
  6. Add reproducible app build/typecheck and automated calculation tests to CI before production readiness. Pages only publishes static documentation.

Merge after checks/review and explicit acceptance or resolution of readiness gaps. The merge updates production docs together with production code.
  5. Deploy the Expo app and apply approved Supabase migrations through their release procedures; Git merge and Pages do not deploy either one.
