1. System overview

UnDebt is a client-rendered household finance planner. Expo/React Native screens collect account and cash-flow assumptions. TypeScript domain modules calculate balances, summaries, and forecasts in the device/browser. Supabase provides email/password authentication, Postgres persistence, and row-level access control through its Data API. There is no application API server, scheduled backend worker, bank aggregator, or server-side projection engine.

  1. getSession() initializes the user; onAuthStateChange() tracks session changes.
  2. Signed-in users trigger select('*').order('created_at', descending); RLS scopes rows.
  3. App.tsx holds rows in React state and derives account subsets and memoized summaries locally.
  4. Account/activity/offset writes update a row, then the app refetches. Projection results are not persisted.
  5. A new linked transfer is stored once and mirrored in calculations. Moving an existing activity between accounts uses two independent writes with best-effort rollback, not a transaction.

Core schema DDL excerpt

The checked-in migration additionally defines RLS policies, grants, update triggers, and a public-table RLS event trigger.

create type public.account_type as enum (
  'HomeLoan', 'CreditCard', 'PersonalLoan', 'BuyNowPayLater', 'CarLoan',
  'Savings', 'Checking', 'Investment', 'TransactionAccount'
);
create type public.offset_type as enum (
  'Full Offset', 'Reduced Interest Rate', 'Capped Percentage Balance', 'No Offset'
);
create table public.accounts (
  account_id uuid primary key default gen_random_uuid(),
  user_id uuid not null default auth.uid() references auth.users(id),
  account_type public.account_type not null,
  title varchar(255),
  balance numeric(15,2) not null,
  start_date date not null default current_date,
  end_date date,
  offset_config jsonb default
    '{"percentage": null, "offset_type": "No Offset", "linked_accounts": []}'::jsonb,
  payments jsonb default '[]'::jsonb,
  interest_rates jsonb default '[]'::jsonb,
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
alter table public.accounts enable row level security;

payments[] stores activities such as {type, amount?, startDate?, frequency?, endDate?, linkedAccountId?}: Income, Payment, Part Payment, Bill Payment, Expense. Production loan schedule is one Principal and Interest payment. interest_rates[] stores {rate, date, endDate?}. offset_config stores type, percentage, linked loan IDs, and compatibility flags. JSON shape and inter-account IDs have no DB constraints.

Access/trigger caveats: RLS is enabled. The migration defines a PUBLIC ownership FOR ALL policy plus four overlapping authenticated CRUD policies. It grants CRUD to anon/authenticated, so RLS is the ownership boundary. Two update triggers both set updated_at. The public-table RLS event trigger logs errors rather than aborting DDL. Review deployed catalog state before relying on or changing these.

npx supabase link --project-ref <project-ref>

Never run remote db push without checking project, migration list, backup/rollback, and review. GitHub Pages does not apply schema changes. The migration file is the source of truth.

SUPABASE_CONFIG in expoapp/config.ts currently contains the hosted project URL and client publishable key; local CLI credentials and dev/prod environment selection are not wired. For local Supabase, use the API URL and anon/publishable key from npx supabase status in a local-only config. The publishable key is not the authorization boundary; never ship service_role in a client.

5. Calculation behavior

All projections are client-side estimates; they are not lender quotes, reconciled transaction history, or financial advice.

Activity and balance reconstruction

  • Dates are ISO YYYY-MM-DD; no frequency means one-off. Recurrence supports days, weeks, fortnights, months, quarters, half-years, and years. Day intervals use fixed day counts; monthly counting anchors to original start and clamps to month-end. Recurring end date is inclusive; no-repeat counts once on start date. Unknown frequency is monthly for activity counting; literal “One-time” is one-off for forecast events but monthly in activity counting.
  • As-of balance = stored balance plus/minus amount × occurrenceCount from max(start_date || created_at-date, activity-start-date) through the requested date. Income adds; Payment debits source and credits linked account; Part Payment debits source and loan; ordinary spending debits cash but increases card/BNPL liability. Other account/activity combinations are not reconciled.
  • Invalid dates in public summary/projection requests throw. Some malformed JSON parsers return no entries and fall back to defaults.

Baseline ambiguity: there is no balance_as_of field. The algorithm adds eligible historical activities to the persisted balance. If a user enters a current balance, recurring past activity can be counted again.

For a recurring activity, N(a;s,e) = max(0, C(e) − C(s−1 day)), where C(d) counts anchored occurrences from entry start through min(d,endDate). Day/week intervals use fixed day counts; month recurrence uses the original day clamped per month. A no-repeat entry counts once only when its start is in the window.

Loan interest and cash projections

periodRate = Σ (annualRateSegment / 100 / periodsPerYear)
                 × (segmentDuration / scheduledPeriodDuration)
interest = max(0, loanBalance - eligibleOffsetBalance) × periodRate
            + proratedChargeInterest

The production loan simulator reads the first payments item as schedule and cadence, ignores its stored start date, and starts the next due payment one frequency interval after the projection cursor (today or FY start), then repeats from that cursor. It adds interest/charges, applies the fixed scheduled amount, then linked additional payments. Payment endDate gates due dates; rate endDate is ignored. Rate changes are duration-prorated inside the interval; this is not daily compounding. The loan-table rate is the first stored rate entry, not necessarily today's active rate.

Cash/account interest uses anniversary windows: each rate segment contributes annualRate/100 × segmentDuration/fullAnniversaryWindowDuration to a simple-interest factor; even a partial final window uses the full anniversary duration as denominator. The window adds max(0, balance) × (factor − 1). Cash-flow events split and restart windows. Linked offset cash does not earn deposit interest in forecasts. Offset allocation is proportional to linked loans' starting balances; partial offset scales cash, capped offset caps the allocation by a share of each loan's starting balance. Allocation is not recomputed from declining simulated debt. Horizon is at most 30 years; charts sample annual balances.

Summary metrics and hard-coded defaults

  • Net worth = assets − debt. Scheduled monthly run-rate = payment amount × frequency periods per year ÷ 12 (daily 365, weekly 52, fortnightly 26, monthly 12, quarterly 4, half-yearly 2, annual 1).
  • Loan screen interest saved = max(0, scheduled interest − actual interest); actual includes offsets and additional payments. This differs from the simulator's separate offset-only comparison.
  • Spend available = starting transaction balances + Income occurrences; spend = Bill Payment + Expense occurrences; after-spend = available − spend. Payment transfers are counted separately but not deducted.
  • Save income/saved values are selected-period occurrence totals. “Cash at period end” reuses Spend available: no savings transfer, expense, or deposit interest is included. Period-start cash is calculated separately, so the two are not opening/closing ledger balances.
  • Month window is as-of + 1 day through addMonths(as-of, N), inclusive; FY is the entire selected year, not clipped to today. July is default.
  • Example-coded defaults: base 4.85%; home +2.10%, car +2.05%, personal +3.65%, card +15.55%, BNPL −4.85%; savings/checking subtract 2.50%. These are static constants, not a live benchmark feed.

5.3 Calculation limitations that change visible values

  1. Stored balance is treated as a baseline plus eligible historical activities; there is no balance-as-of date. Current statement balances may double-count past recurring entries.
  2. Activity counting anchors monthly dates to original start (Jan 30 → Feb 28 → Mar 30); forecast generation advances from prior date (Jan 30 → Feb 28 → Mar 31). Counts/dates can diverge.
  3. Rate endDate is not enforced; before the first dated rate, an existing rate array yields 0%. UI rate labels show the first array item.
  4. Loan interest uses frequency-period simple prorating, then charges, scheduled payment, additional payment. Extra payment only reduces interest after its forecast interval; offset is sampled at interval end and used for the whole interval.
  5. Offset proportions and caps use starting debt; offset cash does not accrue deposit interest. “Offset balance” cards do not show effective interest-offset principal.
  6. Annual chart samples use calendar +12-month dates. Offset end-date calculations can use +365.2425 days; FY loan samples at index 1 are next FY start, while FY end cash is the prior day.
  7. Negative transaction balances can appear in historical totals, but annual series clamp initial cash to zero; loan simulation also clamps starting debt while some debt cards sum signed balances. No taxes, inflation, conversion, bank reconciliation, full fee/charge model, or cash-availability constraint is applied.

6. Gaps and technical risks

  • JSONB arrays have no schema constraints, event history, relational links, conflict detection, or safe concurrent merge.
  • No bank integration, multi-currency conversion, budget engine, export/restore, offline sync, automated test suite, or full CI app build is present.
  • Currency/financial-year settings are client state, not a durable preferences model. There is no stage-specific Supabase configuration; config.ts points to one hosted project. Cross-account transfer edits are not atomic.
  • JSON offset labels drift from the unused DB enum (Partial Offset vs Reduced Interest Rate; Capped Offset vs Capped Percentage Balance).
  • Offset labels drift from the unused DB enum. Rate selection uses start dates; stored endDate values do not independently deactivate rates. Redundant RLS policies/triggers, timezone boundaries, malformed legacy JSON, and financial assumptions need tests and reviewed migrations.

7. Deployment, branch, and merge policy

  1. main is production; dev is proposed/integration. Production docs describe the exact production commit, not future work.
  2. For every material app behavior change on dev, update docs/dev.md and docs/dev.html. The workflow verifies both are included.
  3. Open reviewed dev → main PR; update production MD/HTML to match the release in that PR. Workflow verifies both files when app code changes.
  4. Review UI/accessibility, financial test cases, data compatibility, RLS/migration plan, and docs. Run cd expoapp && npx tsc --noEmit and available app/platform checks. Merge after approval; merged docs become the new production record.
  5. GitHub Pages serves static design pages from branch dev, path /docs, at the docs site. The Actions workflow also validates documentation and publishes on dev pushes. It does not host Expo or apply Supabase migrations. App distribution and database migration apply are separate release steps.
