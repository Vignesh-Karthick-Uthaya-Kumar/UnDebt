UnDebt — Production design

Status: As-is baseline from main (production), not a target-state specification.

Architecture

  • Client: Expo, React Native, TypeScript, and React Native Web. expoapp/App.tsx owns authentication state, account data, navigation, and calculations; screens/components render the UI.
  • Backend: Supabase Auth and Postgres. The Supabase JS client uses a project URL and public client key from expoapp/config.ts. Authenticated clients read/write public.accounts; Postgres RLS scopes rows to the signed-in user.
  • Flow: Sign up/sign in → fetch account rows → calculate summaries/forecasts locally → persist account or JSON data → refetch. There is no separate API server or server-side projection engine.
  • Expo supports native and web development. GitHub Pages hosts static documentation only, not the financial app.

UI and features

Overview, Loans, Accounts, Loan management (offsets), Save, Spend, Help & guides, and Settings. Users manage accounts, loans, income, savings transfers, bills, expenses, and offsets; view balances, interest, net worth, charts, and projections; select series and periods; and use email/password authentication. Layout adapts to available width.

Types: HomeLoan, CreditCard, PersonalLoan, BuyNowPayLater, CarLoan, Savings, Checking, Investment, and TransactionAccount.

Database model

Table/columnPersisted definition
accounts.account_idGenerated UUID primary key
user_idUUID defaulting to auth.uid(); FK to auth.users(id)
account_typeRequired enum with the nine account types above
title, balanceNullable varchar(255); required numeric(15,2)
start_date, end_dateRequired date defaulting to current date; nullable date
offset_configJSONB default with offset type, percentage, and linked account IDs
payments, interest_ratesJSONB arrays for activities/schedules and dated rates
created_at, updated_atTime-zone timestamps; update triggers maintain updated_at

Indexes cover account type, user ID, and GIN-indexed payment/rate JSON. No transaction, repayment, profile, or audit-history table exists. Application JSON shapes are not enforced by a database JSON schema.

payments[] stores objects such as {type, amount?, startDate, frequency?, endDate?, linkedAccountId?}, including Income, Payment, Part Payment, Bill Payment, and Expense. interest_rates[] uses {rate, date, endDate?}; offset_config uses offset_type, optional percentage, and linked_accounts.

Calculations and data interactions

  • Balances as of a date apply eligible payment occurrences since the later of the saved account baseline and entry start date. Income increases balances; payments/expenses adjust balances by entry and account type; linked transfers can update both sides.
  • Recurrence supports daily, weekly, fortnightly, monthly, quarterly, half-yearly, and yearly patterns. Month-based occurrences clamp to the last valid calendar day.
  • Loan projections simulate periodic interest and scheduled repayments with dated rates, charges, additional payments, and linked offsets; the horizon is capped at 30 years. Offset interest is estimated using loan balance less eligible offset funds, bounded by the balance.
  • Net worth = assets − debt. Save/Spend totals cover one-to-twelve-month or financial-year periods. July–June is the default financial year; Settings can change its start month.

Assumption: These are planning estimates, not lender statements or financial advice. Rates, compounding, payment timing, fees, and rounding may differ from institutions.

Gaps and risks

  1. JSONB arrays allow inconsistent payloads and complicate constraints, reporting, history, and concurrent edits.
  2. Calculations are client-side; there is no shared server contract or saved calculation snapshot.
  3. No bank-feed/import, currency conversion, transaction ledger, export/backup, or automated regression suite is present.
  4. The migration has overlapping RLS policies and multiple account update triggers. Verify deployed policies and trigger behavior before modifying schema/permissions.
  5. Projection assumptions/defaults are code constants; assumptions and estimate warnings need explicit product treatment.

Deployment and merge policy

main is production; dev is proposed. Update both dev design files for material code behavior changes or explicit design refreshes. In a reviewed dev → main PR, update production.md and production.html to describe the exact release; the workflow enforces this for application-code changes. Assess calculations and migration/RLS; run cd expoapp && npx tsc --noEmit plus platform checks. Merge only after approval/validation; the merge makes the production docs current with code. GitHub Actions publishes static docs/ on dev pushes after Pages is configured to use GitHub Actions. App hosting and Supabase migration deployment are separate release steps.
